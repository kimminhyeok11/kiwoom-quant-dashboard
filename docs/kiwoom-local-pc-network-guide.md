# 키움 REST API 로컬 PC 운영 가이드

## 목적과 적용 범위

이 문서는 **사용자 컴퓨터에서 키움 REST API를 안정적으로 호출하여 실제 시세를 수집하고 연구 결과를 동기화하는 방법**을 정리한다. 대시보드는 결과 조회와 연구 기록을 담당하고, 키움 OAuth·시세 수집은 지정 단말로 등록된 로컬 PC가 수행한다. 키움은 인증정보 탈취 방지를 목적으로 허용된 IP에서만 API 요청을 허용한다고 안내한다.[1]

> **핵심 원칙:** 키움이 확인하는 값은 PC 이름이나 공유기 내부 주소가 아니라, API 요청이 인터넷으로 나갈 때의 **공인 출발지 IP**다. `192.168.x.x` 같은 사설 IPv4는 등록 대상이 아니다.

| 구성 요소 | 담당 역할 | 운영 위치 | 키움 주문 API 호출 |
|---|---|---|---|
| 로컬 연구 노드 | OAuth·ka10081 일봉·ka10080 1분봉 수집 및 서버 동기화 | 키움 지정 단말로 등록된 사용자 PC | 없음 |
| 로컬 모의 주문 실행기 | 계획 조회·모의 주문 전송·체결/포지션 동기화 | 사용자 PC | 모의투자 정책이 활성일 때만 |
| 공개 대시보드 | 저장된 실제 원본·연구 결과·장중 기록 조회 | 웹 호스팅 | 없음 |

## 네트워크 구성 기준

가정용 회선은 공인 IP가 바뀔 수 있으므로, 무인 운영 수준에 따라 다음 중 하나를 선택한다. 동적 DNS는 도메인만 현재 IP로 연결할 뿐, 키움에 보이는 출발지 IP를 고정하지 않으므로 지정 IP 문제의 해결책이 아니다.

| 운영 방식 | 적합한 경우 | 장점 | 주의점 |
|---|---|---|---|
| 가정용 유동 공인 IP + 변경 시 재등록 | 수동 확인이 가능한 개인 연구 | 추가 회선 비용 없음 | IP 변경 뒤 8050 등 접근 실패 시 키움 지정 단말 IP를 갱신해야 함 |
| 통신사 고정 공인 IP | 24시간 자동 수집·무인 연구 | 지정 IP가 유지돼 가장 단순 | 공유기 교체·회선 이전 때 공인 IP를 다시 확인 |
| 고정 egress가 보장된 서버 | PC 의존성을 제거하려는 경우 | 서버가 계속 실행 | 실제 키움 요청을 그 서버에서 보내므로 해당 서버 IP를 등록해야 함 |

로컬 PC에서는 공유기 관리 화면이나 외부 IP 확인 서비스로 **현재 공인 IP**를 주기적으로 비교하고, 값이 바뀌면 수집을 재개하기 전에 지정 단말 등록 상태를 확인한다. IP 변경 여부는 하루 한 번과 OAuth 8050 오류 발생 시에만 점검하면 충분하다. 수집기 실행마다 외부 IP 확인 서비스를 호출할 필요는 없다.

## OAuth와 자격증명

키움의 접근토큰 발급은 운영 도메인 `https://api.kiwoom.com`, 모의투자 도메인 `https://mockapi.kiwoom.com`의 `/oauth2/token`에 `client_credentials`, App Key, Secret Key를 JSON으로 보내는 방식이다.[2] 키와 토큰은 브라우저·공개 대시보드·Git·로그에 넣지 않고 로컬 `.env`에만 보관한다.

| 항목 | 권장 운영 방식 |
|---|---|
| App Key / Secret Key | 로컬 `.env`만 사용하고 화면·로그·소스 저장소에는 기록하지 않음 |
| 토큰 | 실행기에만 잠시 보관하고, 재시작 시 새로 발급 가능하도록 구성 |
| 모드 분리 | `KIWOOM_DATA_API_MODE=live`는 실제 시세 수집, 주문 모드는 별도 환경값으로 분리 |
| 시간 제한 | OAuth·키움 TR·대시보드 동기화 요청 각각에 제한 시간을 적용해 무한 대기를 막음 |
| 재시도 | 네트워크·5xx·일시적 게이트웨이 오류만 제한적으로 재시도하고, 401·8050·입력 오류는 즉시 원인을 기록 |

## Windows 예약 작업 운영

현재 로컬 PC는 아래 세 작업으로 구성한다. 작업은 `Ready` 상태여야 하고, 마지막 실행 결과는 `0`이 정상 종료를 뜻한다.

| 작업 | 기본 주기 | 역할 | 정상 로그의 기준 |
|---|---|---|---|
| `KiwoomIntradayMinuteCollector` | 평일 09:00~15:31, 1분 | ka10080 실제 1분봉 수집·서버 동기화 | `status: "synced"` 또는 장 마감 정상 `idle` |
| `KiwoomAutomaticOrderExecutor` | 평일 09:01~15:32, 1분 | 모의 주문 계획·체결·포지션 동기화 | 정책·계좌·신호 조건에 따른 안전 대기 또는 동기화 기록 |
| `KiwoomDailyBarResearch` | 평일 15:45 | ka10081 일봉 수집·불변 데이터셋·자동 연구 | 일봉 동기화 후 `completed/ready` |

수집기에는 중복 실행을 막는 잠금 디렉터리가 있다. 프로세스가 비정상 종료돼 잠금만 남으면 다음 예약 작업이 즉시 `0`으로 끝나면서 실제 수집을 건너뛸 수 있다. 이 경우에는 **실행 중인 `minute-bar-collector.mjs` 프로세스가 없는 것을 먼저 확인한 뒤** `.minute-collector.lock`만 제거한다. 실행 중인 프로세스가 있을 때 잠금을 지우면 중복 수집이 발생할 수 있다.

## 정상 대기와 장애의 구분

아래 상태는 주문·데이터 호출이 필요한 오류가 아니라 정상적인 운영 경계다. 수집기는 이 상태를 오류 코드가 아닌 `idle`로 기록하고 종료해야 한다.

| 서버 상태 | 해석 | 실행기 동작 |
|---|---|---|
| `market_closed` | 장 마감 후 당일 실험이 닫힘 | OAuth·시세·주문 호출 없이 정상 종료 |
| `waiting_for_data` | 장중 실험/저장 데이터 준비 전 | 정상 대기 후 다음 주기에 재확인 |
| `waiting_for_intraday_experiment` | 당일 추적 실험 생성 전 | 정상 대기 후 다음 주기에 재확인 |
| `waiting_for_experiment` / `no_tracking_experiment` | 같은 의미의 호환 상태 | 정상 대기 후 다음 주기에 재확인 |
| 8050 | 키움 지정 단말 공인 IP 미허용 | IP 등록 상태를 확인하고 반복 호출 중단 |
| 8030 | `KIWOOM_API_MODE`와 App Key·Secret Key의 실전/모의 구분 불일치 | 주문·계좌·체결 API 호출 없이 `credential_mode_mismatch` 안전 대기로 전환 |
| 401 / 403 | 토큰·권한·노드 인증 문제 | 비밀값·토큰·노드 인증을 확인하고 반복 호출 중단 |

## API Query Error와 종목명 표시 점검 결과

대시보드의 장중 화면은 여러 tRPC 조회를 한 번에 호출한다. 일시적 504·HTML 응답 또는 배치 응답 일부 누락이 발생하면, 최신 전송 계층은 GET 요청을 제한적으로 재시도하고도 정상 JSON 응답을 얻지 못한 경우 **어떤 배치 절차와 어느 응답 인덱스가 누락됐는지 포함한 오류**로 변환한다. 화면은 전체 페이지가 깨지는 대신 ‘장중 기록을 불러오지 못했습니다’와 재시도 안내를 표시한다.

종목명은 저장된 이름이 종목코드와 같거나 비어 있을 때 공용 KRX 유니버스 메타데이터로 보정한다. 예를 들어 `036930`은 **주성엔지니어링**, `005930`은 **삼성전자**로 표시한다. 카드에서 `전체 조건·차트 보기`를 선택하면 저장된 ka10080 실제 1분봉 위의 모의 진입·청산 시점과 축약 없는 전체 규칙 트리를 조회한다.

2026-08-20 09:20 KST의 실제 예약 실행에서는 19종목에서 원시 17,100개, 당일 완결 1분봉 399개를 읽고 380개 봉·19개 최신 가격을 서버에 동기화했다. 실패 종목은 없었다. 이 기록은 로컬 PC의 공인 IP·OAuth·1분봉 수집·서버 동기화 경로가 당시 정상 동작했다는 운영 증거다.

## 빠른 장애 점검 순서

1. Windows 작업 스케줄러에서 세 작업이 `Ready`인지, 마지막 결과가 `0`인지 확인한다.
2. 수집 로그에서 `status: "synced"`, `status: "idle"`, 8050, 401/403, 시간 초과를 구분한다.
3. `synced`가 없고 작업 결과만 계속 `0`이면 실행 중인 프로세스가 없는지 확인한 뒤 오래된 잠금만 제거한다.
4. 8050이면 현재 공인 IP와 키움 지정 단말 등록값을 대조한다. 사설 IP는 비교하지 않는다.
5. 8030이면 주문 실행기를 계속 재실행하지 말고 `.env`의 `KIWOOM_API_MODE`와 App Key·Secret Key가 모두 같은 **모의** 또는 같은 **실전** 구분인지 대조한다. 현재 실행기는 동일 자격증명·같은 거래일의 8030을 `credential_mode_mismatch`로 기록하고 주문·계좌·체결 호출을 하지 않는다.
6. API Query Error가 화면에 나오면 잠시 뒤 다시 조회한다. 지속 시 오류에 포함된 배치 절차·누락 인덱스와 서버 로그를 함께 확인한다.
7. 종목명이 코드로만 보이면 최신 공개 자산이 로드됐는지 확인하고, 카드의 전체 조건·차트 보기를 다시 선택한다.
